# Fillip OAuth resource binding

ChatGPT and other hosts expect the access token `aud` to include this server's MCP resource (`APP_BASE_URL/mcp`). The hook in `oauth_resource_binding.sql` does that. It follows the same shape as Desk, and reads the resource from `fillip_private.settings` so the host is not hardcoded.

## Apply once

1. Run `schema.sql` in the Supabase SQL editor.
2. Run `oauth_resource_binding.sql`.
3. Set the resource to the public origin plus `/mcp`:

```sql
update fillip_private.settings
set value = 'https://YOUR_HOST/mcp'
where key = 'mcp_resource';
```

4. Supabase Dashboard → Authentication → Auth Hooks → Customize Access Token Claims → `public.fillip_access_token_hook`.
5. Authentication → URL configuration: add `APP_BASE_URL` and `APP_BASE_URL/oauth/consent` as redirect URLs.
6. Sign-in is an emailed one-time code. The consent page calls `signInWithOtp` with `shouldCreateUser: true`, because that code is how a new account is created, and it does not add user fields beyond the account Supabase creates. Fillip's own reply is the same whether or not the email already had an account: status text `If that email can sign in, a code is on its way.`, after a short wait so the two outcomes take a similar amount of time. Residual: Supabase's public `/otp` endpoint with `create_user=false` still returns `otp_disabled` to anyone holding the anon key. Fillip cannot close that. Authentication → Providers → Email stays on. Authentication → Emails → Magic Link must include `{{ .Token }}` so the message shows the code. Enable custom SMTP with Resend (`smtp.resend.com`, port 465, username `resend`, password your Resend API key, from-address on the verified domain). That avoids Supabase's built-in email rate limit. Set `FILLIP_AUTH_GOOGLE_ENABLED=true` only after the Google provider is enabled. Until then the consent page does not show Google. Password sign-in remains behind "Use a password instead".
7. Fillip does not publish `/.well-known/oauth-authorization-server`. Supabase does, and that document is where PKCE and `authorization_response_iss_parameter_supported` belong. Supabase currently advertises both `S256` and `plain`. Claude, Cursor, ChatGPT, and Grok send `S256`. There is no dashboard setting that disables `plain`, and Supabase has approved `plain` authorizations. Fillip cannot remove `plain` from Supabase's document. Real clients go straight to Supabase's authorize endpoint, so the `fillip_pkce` cookie check never runs. The access-token hook withholds the `/mcp` audience unless that grant's `code_challenge_method` is `s256`, so a plain or missing-PKCE token cannot be used on `/mcp`. That check stays an inert no-op when the cookie is absent. Fillip still rejects a missing `code_challenge`, a missing `code_challenge_method`, and any method other than `S256` on `GET /oauth/authorize` when a client uses that route. A successful S256 request stores the proof in a short-lived HttpOnly cookie named `fillip_pkce`. The consent page denies a method or challenge that is actually present and is not exact S256. When the details already include `redirect_url`, the page assigns that URL immediately, before it reads the client and before the PKCE check, and it does not call approve again. When `redirect_url` is absent and both PKCE fields are omitted, the page shows Connect. Authorization codes are single-use and short-lived. Calling approve after Supabase has already issued a code invalidates that code. Fillip's protected-resource metadata does not advertise `plain` and does not set `authorization_response_iss_parameter_supported`, because that flag is an authorization-server field. Supabase does not send the `iss` parameter.
8. Authentication → Sessions: set the refresh-token reuse interval to 0. A reused refresh token then revokes the chain.
9. The access-token hook adds the Fillip `/mcp` audience only for the authorization the code was issued from: the approved `auth.oauth_authorizations` row with a non-null `authorization_code` whose client, user, and scope match the session written for that exchange, whose resource string-equals `mcp_resource`, and whose `code_challenge_method` is `s256`. A pending authorization for the same user and client is not read. Two issued codes that share a scope are ambiguous and neither is bound. Residual: an issued grant with no resource does not receive the audience, the same as Stetwise. A trailing slash does not match. An expired row is not the issued grant. A refresh uses the stored session row only, and only when that stored value still equals the setting, even if a later approval names something else. Another client's authorization cannot cause a match. After the public URL changes, update `mcp_resource`, then disconnect clients at `/connections` and connect again.
10. When the authorization details already include `redirect_url`, the page assigns that URL immediately, before it reads the client and before the PKCE check. It does not call approve again, because a second approve invalidates the single-use code. When `redirect_url` is absent, the page shows Connect. Supabase's authorize endpoint can still skip the page when a session cookie and an existing grant already exist, because clients build that URL from Supabase's metadata and Fillip cannot add `prompt=consent`. Reusing a stored refresh token is not a new authorization and does not show consent.
