# Fillip OAuth resource binding

ChatGPT and other hosts expect the access token `aud` to include this server's MCP resource (`APP_BASE_URL/mcp`). The hook in `oauth_resource_binding.sql` does that. It follows the same shape as Desk, and reads the resource from `fillip_private.settings` so the host is not hardcoded.

## Apply once

1. Run `schema.sql` in the Supabase SQL editor.
2. Run `oauth_resource_binding.sql`.
3. Set the resource to the public origin plus `/mcp`:

```sql
update fillip_private.settings
set value = 'https://YOUR_HOST/mcp'
where key = 'mcp_resource';
```

4. Supabase Dashboard → Authentication → Auth Hooks → Customize Access Token Claims → `public.fillip_access_token_hook`.
5. Authentication → URL configuration: add `APP_BASE_URL` and `APP_BASE_URL/oauth/consent` as redirect URLs.
6. Sign-in is an emailed one-time code. The browser calls Fillip `POST /auth/code/send` and `POST /auth/code/verify`. Fillip calls Supabase with `create_user` true, because that code is how a new account is created, and it does not add user fields beyond the account Supabase creates. There is no `emailRedirectTo`. The send response is the same status and the same text whether or not the account exists: `If that email can sign in, a code is on its way.`, after a short wait so the two outcomes take a similar amount of time. Wrong verifies are counted in `fillip_code_attempts` per hashed email and per hashed IP. That table is service-role only, row level security is on, and it stores no raw email and no raw code. Five wrong codes in 15 minutes lock that email for 15 minutes, and Fillip says `Too many wrong codes. Request a new one.` A wrong code answers `That code is wrong or expired.` for every account. A new send does not clear that lock. The lockout covers only Fillip's routes. On Vercel the per-IP key is `x-vercel-forwarded-for` or `x-real-ip`, and an IPv6 address is keyed on its /64. `FILLIP_LOCKOUT_SECRET` is the hash key. When it is unset, Fillip uses `FILLIP_UNSUBSCRIBE_SECRET`. Rotating the secret that is the hash key resets the counters. Rotating `FILLIP_UNSUBSCRIBE_SECRET` resets them when `FILLIP_LOCKOUT_SECRET` is empty. A correct code returns the session tokens only on that same-origin response. The consent page calls `setSession` and continues the existing consent flow. Your data and Connected applications offer Sign out everywhere. Residual: Supabase's public `/otp` endpoint with `create_user=false` still returns `otp_disabled` to anyone holding the anon key. A direct Supabase `/auth/v1/verify` with the anon key is backstopped only by Supabase's own limit. Fillip cannot close either of those. Authentication → Providers → Email stays on. Authentication → Emails → Magic Link must include `{{ .Token }}` so the message shows the code. Enable custom SMTP with Resend (`smtp.resend.com`, port 465, username `resend`, password your Resend API key, from-address on the verified domain). That avoids Supabase's built-in email rate limit. Set `FILLIP_AUTH_GOOGLE_ENABLED=true` only after the Google provider is enabled. Until then the consent page does not show Google. Password sign-in remains behind "Use a password instead".
7. Fillip does not publish `/.well-known/oauth-authorization-server`. Supabase does, and that document is where PKCE and `authorization_response_iss_parameter_supported` belong. Supabase currently advertises both `S256` and `plain`. Claude, Cursor, ChatGPT, and Grok send `S256`. There is no dashboard setting that disables `plain`, and Supabase has approved `plain` authorizations. Fillip cannot remove `plain` from Supabase's document. Real clients go straight to Supabase's authorize endpoint, so the `fillip_pkce` cookie check never runs. The access-token hook withholds the `/mcp` audience unless that grant's `code_challenge_method` is `s256`, so a plain or missing-PKCE token cannot be used on `/mcp`. That check stays an inert no-op when the cookie is absent. Fillip still rejects a missing `code_challenge`, a missing `code_challenge_method`, and any method other than `S256` on `GET /oauth/authorize` when a client uses that route. A successful S256 request stores the proof in a short-lived HttpOnly cookie named `fillip_pkce`. The consent page denies a method or challenge that is actually present and is not exact S256. When the details already include `redirect_url`, the page assigns that URL immediately, before it reads the client and before the PKCE check, and it does not call approve again. When `redirect_url` is absent and both PKCE fields are omitted, the page shows Connect. Authorization codes are single-use and short-lived. Calling approve after Supabase has already issued a code invalidates that code. Fillip's protected-resource metadata does not advertise `plain` and does not set `authorization_response_iss_parameter_supported`, because that flag is an authorization-server field. Supabase does not send the `iss` parameter. The refresh-token reuse residual is the next paragraph.
8. Refresh-token reuse residual: Supabase accepts reuse of the immediate parent refresh token and returns the same active child, rejects older tokens, and does not revoke the chain. Setting the reuse interval to 0 does not close that. The mitigation is an access-token expiry of 900 seconds under Authentication → Sessions, plus Sign out everywhere. That action revokes every OAuth grant through `DELETE /auth/v1/user/oauth/grants?client_id=` and then revokes every refresh token through `POST /auth/v1/logout?scope=global`. GoTrue's admin API manages OAuth clients only. It has no admin route that deletes grants or authorizations, so Fillip uses the signed-in user grant API and then global logout. Fillip does not detect `refresh_token_already_used`. Clients refresh directly at Supabase `/token`, and GoTrue rejects a reused refresh token before the access-token hook runs, so this server never sees that signal.
9. The access-token hook adds the Fillip `/mcp` audience only for the authorization the code was issued from: the approved `auth.oauth_authorizations` row with a non-null `authorization_code` whose client, user, and scope match the session written for that exchange, whose resource string-equals `mcp_resource`, and whose `code_challenge_method` is `s256`. A pending authorization for the same user and client is not read. Every unexpired, approved, issued authorization for that user, client, and scope receives the audience when each resource equals `mcp_resource` and each `code_challenge_method` is `s256`, however many rows there are. The audience is withheld if any of those rows has a different or null resource or a method other than `s256`. When the claims include an authorization id, that row is matched instead. Residual: an issued grant with no resource does not receive the audience, the same as Stetwise. A trailing slash does not match. An expired row is not the issued grant. A refresh uses the stored session row only, and only when that stored value still equals the setting, even if a later approval names something else. Another client's authorization cannot cause a match. After the public URL changes, update `mcp_resource`, then disconnect clients at `/connections` and connect again. The Supabase `/otp` `create_user=false` residual is stated with the emailed-code route above. The refresh-token reuse residual is the previous paragraph.
10. When the authorization details already include `redirect_url`, the page assigns that URL immediately, before it reads the client and before the PKCE check. It does not call approve again, because a second approve invalidates the single-use code. When `redirect_url` is absent, the page shows Connect. Supabase's authorize endpoint can still skip the page when a session cookie and an existing grant already exist, because clients build that URL from Supabase's metadata and Fillip cannot add `prompt=consent`. Reusing a stored refresh token is not a new authorization and does not show consent.
